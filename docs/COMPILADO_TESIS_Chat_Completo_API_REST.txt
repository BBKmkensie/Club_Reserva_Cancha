################################################################################
# A. ¿QUÉ ES UNA API REST?
################################################################################

Una API REST es una forma estándar de que dos programas se comuniquen por
internet usando URLs y métodos HTTP.

--------------------------------------------------------------------------------
En simple
--------------------------------------------------------------------------------
Imagina un mesero:

  • Tú (frontend Angular) = cliente que pide algo
  • La cocina (backend NestJS + PostgreSQL) = servidor que prepara la respuesta
  • El mesero = la API

La API no es la base de datos ni la pantalla: es el PUENTE entre ambos.

--------------------------------------------------------------------------------
Qué significa cada letra
--------------------------------------------------------------------------------
  Término    Significado
  ---------  ----------------------------------------------------------------
  API        Application Programming Interface = interfaz para que programas
             hablen entre sí
  REST       Estilo de diseño: recursos con URLs + verbos HTTP + JSON

RESTful = API diseñada siguiendo ese estilo.

--------------------------------------------------------------------------------
Cómo funciona
--------------------------------------------------------------------------------
  1. El cliente hace una petición HTTP a una URL
  2. El servidor procesa (lee/escribe en BD, valida, etc.)
  3. Responde con datos (casi siempre JSON) y un código:
       200 = ok
       401 = no autorizado
       404 = no encontrado
       409 = conflicto (ej. cancha ocupada, sin cupo)

En tu proyecto:

  Login en Angular
      → POST http://localhost:3000/auth/login
      → NestJS valida usuario
      → Responde { accessToken, user }
      → Angular guarda el token y muestra el dashboard

--------------------------------------------------------------------------------
Los “verbos” HTTP (lo más importante)
--------------------------------------------------------------------------------
  Método    Acción típica              Ejemplo en tu app
  --------  -------------------------  --------------------------------------
  GET       Leer                       GET /taller → listar talleres
  POST      Crear o acción             POST /auth/login → iniciar sesión
  PATCH     Cambiar parte              PATCH /alumno/5 → editar dato
  PUT       Reemplazar / guardar set   PUT /periodo  → configurar período
  DELETE    Borrar                     DELETE /reserva/3

Misma URL, distinta acción:

  GET    /alumno/5   → “dame el alumno 5”
  DELETE /alumno/5   → “borra el alumno 5”

--------------------------------------------------------------------------------
Características de REST
--------------------------------------------------------------------------------
  • Recursos con URL → /taller, /alumno, /reserva
  • Sin estado de sesión clásica en el servidor → cada request lleva lo
    necesario (en tu caso el JWT en el header Authorization)
  • JSON como formato de intercambio
  • Métodos HTTP claros → GET lee, POST crea, etc.

--------------------------------------------------------------------------------
En tu proyecto (concreto)
--------------------------------------------------------------------------------
  Pieza                    Qué es
  -----------------------  --------------------------------------------------
  Angular ApiService       Cliente que llama a la API
  NestJS @Controller       La API REST real
  http://localhost:3000    Base de la API
  Swagger /api/docs        Catálogo visual de endpoints

No usas una API de terceros: tú construiste tu propia API REST para talleres,
cancha, salidas, asistencia, apoderados, etc.

--------------------------------------------------------------------------------
Analogía rápida
--------------------------------------------------------------------------------
  GET    = mirar el menú
  POST   = pedir un plato nuevo
  PATCH  = cambiar la bebida del pedido
  DELETE = cancelar el pedido

Eso es una API REST: pedir y modificar recursos por HTTP de forma ordenada.

--------------------------------------------------------------------------------
Puente con TypeORM y PostgreSQL
--------------------------------------------------------------------------------
  Angular  --HTTP/JSON-->  Nest Controller  -->  Service  -->  TypeORM  -->  PostgreSQL
                ↑__________________________ respuesta JSON ___________________|

La API REST es la capa HTTP. TypeORM no es la API: es el traductor a la BD.

# B. CHEAT SHEET — 6 FLUJOS
################################################################################

FÓRMULA UNIVERSAL
-----------------
  Angular (página)  envía HTTP
  Nest Controller  recibe URL / body   (no hace la regla difícil)
  Nest Service     aplica negocio      (cupos, estados, solapes…)
  TypeORM          lee/escribe
  PostgreSQL       guarda

  Frontend:  frontend/src/app/pages/…  +  services/api.service.ts
  Backend:   src/<modulo>/             +  src/entities/


1) LOGIN — Quién: todos
   Pantalla: login
   API: POST /auth/login { usuario, password }
   Service: AuthService → hash + JWT
   Después: interceptor Bearer; apoderado→portal | resto→dashboard

2) TALLER — Quién: coordinación
   Estados: BORRADOR → ESPERA_DOCENTE → ESPERA_HORARIO → PUBLICADO → CERRADO
   Pasos: crear → asignar docente → aceptar → horario → publicar
   Solo PUBLICADO sale en catálogo

3) INSCRIPCIÓN — Quién: alumno + profesor
   validar → PENDIENTE → ACEPTADO|RECHAZADO
   Cupo = capacidad − (PENDIENTE+ACEPTADO)
   Unique alumno+taller

4) ASISTENCIA — Quién: profesor
   abrir sesión → guardar lista → cerrar
   Solo alumnos ACEPTADOS; al cerrar: alertas + mail apoderado

5) RESERVA CANCHA — Quién: profesor/coordinación
   disponibilidad → POST /reserva
   Franja activa + sin solape de horarios

6) PORTAL APODERADO — Quién: apoderado
   JWT.sub = id del hijo; GET /apoderado/resumen
   Lee talleres ACEPTADOS + sesiones CERRADAS

QUIÉN HACE QUÉ
  Coordinación: taller, período, propuestas, franjas, reportes
  Profesor: aceptar inscripción, lista, reservas, salidas
  Alumno: inscribirse, catálogo, salidas
  Apoderado: ver hijo/asistencia, proponer

FRASES DEFENSA
  • Controller delgado, reglas en el Service
  • Estado del taller controla cuándo se puede inscribir
  • Cupo y solape se validan antes del INSERT; BD refuerza con unique/FK
  • Apoderado autentica con datos del alumno; portal lee sesiones CERRADAS
  • JWT: un login; Bearer vía interceptor

# C. EXPLICACIÓN SIMPLE (como se explicó en el chat)
################################################################################

El sistema en una frase
-----------------------
Página web del colegio para talleres: anotar alumnos, pasar lista,
reservar cancha y avisar al apoderado.

Analogía restaurante
--------------------
  Frontend Angular     = menú y mesas (lo que ves)
  Backend NestJS       = cocina (las reglas)
  PostgreSQL           = inventario / libro de pedidos
  API REST             = el mesero

Patrón de carpetas backend
--------------------------
  reserva/
    reserva.controller.ts  → la puerta (URL)
    reserva.service.ts     → el cerebro (reglas)
    entities/reserva…      → la tabla

Historia completa (camino feliz)
--------------------------------
  Día 1: coordinación crea taller (BORRADOR)
  Día 2: asigna profesor → acepta → horario → PUBLICADO
  Día 3: alumno valida + solicita → PENDIENTE → profesor ACEPTA
  Día 4: reserva cancha (sin solape)
  Día 5: profesor pasa lista y cierra → mail/portal apoderado

Cómo leer código sin marearte
-----------------------------
  *.controller.ts  → ¿qué URL?
  *.service.ts     → ¿qué reglas?
  *.entity.ts      → ¿qué tabla?
  *.component.ts   → ¿qué pantalla?
  api.service.ts   → ¿qué llama al backend?

2. BACKEND — NestJS + TypeScript + Node.js + TypeORM
================================================================================

¿Qué es cada cosa?
------------------
• Node.js     Entorno que ejecuta JavaScript/TypeScript en el servidor.
• TypeScript  Lenguaje tipado; se compila a JavaScript antes de correr.
• NestJS      Framework que organiza el API en módulos, controladores y
              servicios (estructura similar a Angular).
• TypeORM     ORM que traduce clases TypeScript ↔ tablas PostgreSQL,
              sin escribir SQL a mano en cada operación.

Cómo está armado en este proyecto
---------------------------------
El backend vive en la raíz del repo (carpeta src/).
El módulo raíz (app.module.ts) conecta:

  1. ConfigModule   → lee .env (host, puerto, usuario, JWT, mail)
  2. TypeOrmModule  → conexión type: 'postgres' a la BD proyecto_taller
  3. Módulos de dominio:
     auth, talleres, alumnos, profesores, reservas, salidas,
     asistencia, apoderados, reportes, etc.

Patrón típico por dominio
-------------------------
  Pieza         Rol
  ------------  ----------------------------------------------------------
  Controller    Recibe HTTP (GET, POST…) y expone rutas
  Service       Lógica de negocio
  Entity        Mapeo de una tabla (src/entities/)
  DTO           Validación del body (class-validator)
  Module        Agrupa controller + service + entidades TypeORM

Ejemplo de flujo:
  Cliente pide “crear reserva”
    → ReservaController
    → ReservaService
    → TypeORM guarda en PostgreSQL
    → Respuesta JSON

También hay:
  • JWT (@nestjs/jwt + Passport) para login y roles
    (admin, profesor, alumno, apoderado, directiva)
  • Nodemailer para correos

Importante:
  synchronize: false  → el esquema NO se inventa al arrancar.
  Las tablas se crean con scripts SQL
  (create_database.sql, proyecto_taller_fixed.sql).

4. BASE DE DATOS — PostgreSQL
================================================================================

¿Qué es?
--------
Motor relacional (tablas, claves foráneas, consultas SQL).
En este proyecto la base se llama: proyecto_taller

Cómo se usa
-----------
• NestJS se conecta con el driver pg vía TypeORM.
• Cada entidad en src/entities/ representa una tabla, por ejemplo:
  - Admin, Alumno, Profesor
  - Taller, TallerHorario, InscripcionTaller
  - Reserva, FranjaCancha
  - Salida, InscripcionSalida
  - SesionAsistencia, RegistroAsistencia

  “buscar alumnos del taller X”
    → genera SQL
    → PostgreSQL responde
    → NestJS lo convierte en objetos
    → Angular los consume como JSON

Credenciales típicas en .env:
  DB_HOST, DB_PORT (5432), DB_USERNAME, DB_PASSWORD, DB_DATABASE

  Navegador (Angular + Tailwind)
          │  HTTP / JSON + JWT
          ▼
  API NestJS (TypeScript en Node.js)

6. MÓDULO AUTH — DE LOGIN A JWT
================================================================================

Flujo completo
--------------
  LoginComponent (Angular)
    → ApiService.loginUnified()
    → POST /auth/login
    → AuthController → AuthService
    → TypeORM busca en Admin / Profesor / Alumno (PostgreSQL)
    → JwtService firma el token
    → Angular guarda sesión + Bearer en cada request

Archivos paso a paso
--------------------

FRONTEND — login.component.ts
  Formulario con Tailwind (bg-surface, bg-primary-500).
  Al entrar llama api.loginUnified(usuario, password).
  Si OK, guarda el token en AuthRoleService y redirige
  (apoderado → portal; resto → dashboard).

FRONTEND — api.service.ts
  POST /auth/login  { usuario, password }
  Sin “tipo”: el backend detecta solo si es admin, profesor,
  alumno o apoderado.

FRONTEND — auth.interceptor.ts
  En cada petición HTTP agrega Authorization: Bearer <token>.
  Si recibe 401, limpia sesión y manda a /login.

BACKEND — auth.module.ts
  Registra:
  • TypeORM con entidades Admin, Profesor, Alumno
  • JWT (secreto y expiración desde .env)
  • Passport + JwtStrategy

BACKEND — auth.controller.ts
  Ruta                    Qué hace
  ----------------------  ----------------------------------------------
  POST /auth/login        Público (@Public()). Valida credenciales
  GET  /auth/me           Con JWT. Devuelve id, nombre, role, tipo

BACKEND — auth.service.ts (lógica real)
  1. Busca el usuario en PostgreSQL según perfil.
  2. Verifica hash/salt de la contraseña (password.util).
  3. Si es primer acceso con la clave por defecto, inicializa el hash.
  4. Construye el payload JWT (sub, role, tipo, tallerId, nombre).
  5. Devuelve { accessToken, user }.

BACKEND — jwt.strategy.ts
  Lee el Bearer, valida firma/expiración y deja el payload
  en req.user para el resto de rutas.

POSTGRESQL
  Tablas: admins, profesores, alumnos
  (RUT, hashes, apoderado_rut, etc.).
  TypeORM: adminRepo.findOne({ where: { email } })
    → SELECT ... FROM admins WHERE email = ...

7. MÓDULO RESERVAS DE CANCHA
================================================================================

Flujo completo
--------------
  ReservasComponent (Angular + Tailwind)
    → ApiService.getDisponibilidadSemana() / createReserva()
    → GET/POST /reserva/...
    → ReservaController → ReservaService
    → TypeORM: tablas reservas + franjas_cancha
    → JSON con slots disponible / ocupada / no_habilitada

Archivos paso a paso
--------------------

FRONTEND — reservas.component.ts
  Página de cancha: elige fecha, ve slots, crea/cancela reservas.
  Usa CanchaSemanaVistaComponent y constantes de horario compartidas
  con el backend.

FRONTEND — api.service.ts (métodos de reserva)
  Método                     Endpoint
  -------------------------  ----------------------------------------------
  Listar                     GET /reserva
  Disponibilidad día         GET /reserva/disponibilidad?fecha=...
  Disponibilidad semana      GET /reserva/disponibilidad-semana
  Crear                      POST /reserva
  Editar / borrar            PATCH / DELETE /reserva/:id

BACKEND — reserva.controller.ts
  Solo HTTP: recibe query/body y delega al service.
  Prefijo “reserva” → rutas como /reserva/disponibilidad-semana.

BACKEND — reserva.service.ts (negocio)
  1. Disponibilidad: carga franjas activas del día + reservas
     existentes → marca cada slot como disponible u ocupada.
  2. Crear: validarReserva() comprueba duración, rango horario,
     franja habilitada y que no haya solapamiento.
  3. Si todo OK → reservaRepository.save(...) en PostgreSQL.

BACKEND — reserva.entity.ts → tabla “reservas”
  Columna TS         Columna SQL       Relación
  -----------------  ----------------  ---------------------------------
  espacio            espacio           —
  fecha              fecha             —
  horaInicio/Fin     hora_inicio/fin   —
  tallerId           taller_id         ManyToOne → Taller
  profesorId         profesor_id       ManyToOne → Profesor
  adminId            admin_id          ManyToOne → Admin

  También usa FranjaCancha (horarios que la directiva habilita).

Resumen por capa (Auth vs Reservas)
-----------------------------------
  Capa         Auth                         Reservas
  -----------  ---------------------------  ----------------------------
  Angular      Formulario + guarda JWT      Grilla visual de slots
  NestJS       Valida usuario y firma       Valida solapes y persiste
  TypeORM      Lee/escribe hashes           CRUD en reservas / franjas
  PostgreSQL   Tablas de personas           Tablas de cancha
  Tailwind     Estilos del login            Estilos de la pantalla

8. MÓDULO TALLERES
================================================================================

Flujo general
-------------
  GestionActividades / Talleres (Angular)
    → ApiService (getTalleres, crear, asignar, horario, publicar…)
    → /taller/*
    → TallerController → TallerService
    → TypeORM: talleres, asignaciones_docente, taller_horario, …
    → PostgreSQL

Ciclo de estados del taller:
  BORRADOR → ESPERA_DOCENTE → ESPERA_HORARIO → PUBLICADO → CERRADO

Frontend
--------
gestion-actividades.component.ts
  Pantalla del coordinador: crear actividad, asignar docente,
  definir horarios, publicar y cerrar.

talleres.component.ts
  CRUD más simple: lista / crea / edita.
  Solo quien tiene canAccessTalleresCRUD() ve “Nuevo Taller”.

api.service.ts — endpoints principales
  Acción              Endpoint
  ------------------  ------------------------------------------------
  Listar              GET /taller
  Catálogo público    GET /taller/catalogo
  Crear               POST /taller
  Asignar docente     POST /taller/:id/asignar-docente
  Horario             PATCH /taller/:id/horario
  Publicar            PATCH /taller/:id/publicar
  Cerrar              PATCH /taller/:id/cerrar
  Detalle/editar/...  GET / PATCH / DELETE /taller/:id

Backend
-------
taller.module.ts
  Registra entidades (Taller, Profesor, AsignacionDocente,
  TallerHorario, InscripcionTaller, etc.) e importa
  NotificacionModule y PeriodoModule.

taller.controller.ts
  Solo HTTP. Importante: rutas estáticas (catalogo,
  asignaciones/pendientes) van ANTES de :id.

taller.service.ts — lógica
  Método                 Qué hace
  ---------------------  ----------------------------------------------
  create                 Inserta con estado BORRADOR
  findCatalogo           Solo PUBLICADO con inscripción abierta
  asignarDocente         Asignación pendiente + notifica profesor
  responderAsignacion    Acepta → ESPERA_HORARIO (o rechaza)
  definirHorario(s)      Reemplaza filas en taller_horario
  publicar               Exige horario + docente → PUBLICADO
  cerrarPeriodo          Solo si publicado → CERRADO

Entidad taller.entity.ts → tabla “talleres”
  Campo                                      Rol
  -----------------------------------------  --------------------------
  tipo, descripcion, capacidad                Datos básicos
  estado                                     Ciclo BORRADOR→CERRADO
  modoHorario                                POR_CURSO o POR_SECCION
  fechaAperturaInscripcion / cierre          Ventana de postulación
  relaciones                                 profesores, horarios,
                                             inscripciones, reservas,
                                             salidas

Ejemplo concreto: publicar una actividad
----------------------------------------
  1. Coordinador crea taller → POST /taller → BORRADOR en PostgreSQL.
  2. Asigna profesor → asignación PENDIENTE + notificación.
  3. Profesor acepta → ESPERA_HORARIO.
  4. Se definen bloques → filas en taller_horario.
  5. Publicar → PUBLICADO → aparece en GET /taller/catalogo.
  6. Al cerrar el período → CERRADO.

10. MÓDULO PORTAL APODERADO
================================================================================

Flujo
-----
  Login (tipo apoderado) → JWT con sub = alumnoId (el hijo)
    → PortalApoderadoComponent
    → GET /apoderado/resumen (+ propuestas)
    → JwtAuthGuard → ApoderadoController → ApoderadoService
    → alumnos, inscripcion_taller, sesiones_asistencia

Frontend
--------
portal-apoderado.component.ts
  Vista solo para apoderados: datos del hijo, talleres inscritos,
  asistencia por taller, catálogo y propuestas a la directiva.
  Tras login, Angular redirige aquí si tipo === 'apoderado'.

api.service.ts
  Acción                   Endpoint
  -----------------------  --------------------------------------------
  Panel principal          GET /apoderado/resumen
  Proponer inscripción     POST /apoderado/proponer-inscripcion/:tallerId
  Mis propuestas           GET /apoderado/mis-propuestas
  Actividad libre          POST /apoderado/proponer-actividad-libre

Backend
-------
apoderado.controller.ts
  Toda la clase con @UseGuards(JwtAuthGuard).

apoderado.service.ts
  • assertApoderado(user) → solo si tipo === 'apoderado';
    devuelve user.sub (id del hijo).
  • getResumen(alumnoId) → hijo + talleres con inscripción ACEPTADA
    + conteo presente/ausente por taller (sesiones CERRADAS).

Cómo se conectan Asistencia y Portal Apoderado
----------------------------------------------
  Profesor cierra sesión de asistencia
          │

24. PREGUNTAS TIPO PROFESOR DE TESIS (CON RESPUESTAS)
================================================================================
Estas son preguntas típicas de una comisión de título sobre ESTE código,
seguidas de una respuesta defendible (incluye limitaciones honestas).

--------------------------------------------------------------------------------
P1. ¿Por qué NestJS + Angular + PostgreSQL y no otra combinación?
--------------------------------------------------------------------------------
RESPUESTA:
Es una arquitectura cliente-servidor clásica en 3 capas:
  - Angular = SPA de presentación (rutas, guards, UI)
  - NestJS = API REST de negocio (módulos, DTOs, JWT)
  - PostgreSQL = persistencia relacional (FK, unique, integridad)

NestJS encaja porque el dominio es rico (talleres, asistencia, salidas,
permisos por rol) y se organiza por módulos (AuthModule, TallerModule…).
TypeScript en ambos lados reduce fricción de contratos (DTOs/models).
PostgreSQL conviene por relaciones fuertes (alumno↔taller↔inscripción↔sesión).

Alternativas descartables en defensa:
  - Monolito PHP/Blade: menos tipado y menos separación API/UI.
  - NoSQL puro: peor para cupos, solapes de cancha y FK.
  - Microservicios: overkill para un proyecto de título de un equipo pequeño.

--------------------------------------------------------------------------------
P2. Explique el flujo de una petición de punta a punta (ej. login).
--------------------------------------------------------------------------------
RESPUESTA:
1) LoginComponent llama ApiService.loginUnified
2) POST /auth/login → AuthController.login (@Public)
3) AuthService busca en Admin/Profesor/Alumno (TypeORM → PostgreSQL)
4) Verifica password (PBKDF2) y firma JWT
5) Frontend guarda accessToken en AuthRoleService
6) authInterceptor agrega Authorization: Bearer en cada request

Código clave (controller):
  @Public()
  @Post('login')
  login(@Body() dto: LoginDto) {
    return this.authService.login(dto);
  }

Interceptor Angular:
  const authReq = token
    ? req.clone({ setHeaders: { Authorization: `Bearer ${token}` } })
    : req;

--------------------------------------------------------------------------------
P3. ¿Cómo garantiza integridad en la base de datos? ¿Por qué synchronize:false?
--------------------------------------------------------------------------------
RESPUESTA:
TypeORM mapea clases (@Entity) a tablas, pero el esquema se aplica con
scripts SQL (create_database.sql / proyecto_taller_fixed.sql).

En app.module.ts:
  synchronize: false,   // NO altera tablas al arrancar
  autoLoadEntities: true,

¿Por qué?
  synchronize:true en producción puede borrar/alterar columnas sin control.
  Con false, el esquema es explícito y versionable (mejor para tesis y despliegue).

Además hay constraints de negocio a nivel ORM, ej.:
  @Entity('inscripcion_taller')
  @Unique(['alumnoId', 'tallerId'])
Eso impide dos postulaciones al mismo taller para el mismo alumno.

--------------------------------------------------------------------------------
P4. ¿Cómo funciona la autenticación y la autorización?
--------------------------------------------------------------------------------
RESPUESTA (técnica + honesta):
Autenticación = JWT con Passport (JwtStrategy lee Bearer, valida firma/exp).
El payload lleva sub, role, tipo, tallerId, nombre.

Autorización = mezcla de:
  - Frontend: authGuard + AuthRoleService (canAccess…, canVer…)
  - Backend selectivo: ej. ApoderadoController con @UseGuards(JwtAuthGuard)
    y assertApoderado(user.tipo === 'apoderado')

JwtAuthGuard:
  - Si @Public() → deja pasar
  - Si no → exige JWT (Passport strategy 'jwt')

LIMITACIÓN HONESTA PARA LA DEFENSA:
Hoy JwtAuthGuard NO está registrado como APP_GUARD global en AppModule;
protege de forma explícita módulos como /apoderado. Varias rutas dependen
más del frontend. Mejoras futuras: APP_GUARD global + RolesGuard por endpoint.

--------------------------------------------------------------------------------
P5. ¿Cómo almacenan las contraseñas? ¿Es seguro?
--------------------------------------------------------------------------------
RESPUESTA:
No se guarda la contraseña en claro. password.util.ts usa PBKDF2-SHA512
con salt aleatorio (crypto nativo de Node):

  const hash = crypto
    .pbkdf2Sync(password, passwordSalt, 1000, 64, 'sha512')
    .toString('hex');

Hay clave temporal de primer acceso ('12345') para seeds/demo educacional,
que se inicializa al primer login correcto (needsPasswordInit).

Limitación defendible: 1000 iteraciones es bajo para producción moderna
(recomendable aumentar; o bcrypt/argon2). En tesis: correcto conceptualmente,
mejorable en hardening.

--------------------------------------------------------------------------------
P6. Explique un ciclo de vida de negocio (taller o asistencia).
--------------------------------------------------------------------------------
RESPUESTA — Taller (máquina de estados):
  BORRADOR → ESPERA_DOCENTE → ESPERA_HORARIO → PUBLICADO → CERRADO

Cada transición se valida en TallerService (no se puede publicar sin horario
ni docente aceptado). Eso evita estados inconsistentes.

RESPUESTA — Asistencia:
  abrirSesion → actualizarAsistencia (listaGuardada) → cerrarSesion
  → evaluarAusenciasRecurrentes → mails a apoderados

Al abrir, se crean registros PRESENTE para inscritos ACEPTADOS.
Al cerrar sin lista guardada → BadRequestException.

--------------------------------------------------------------------------------
P7. ¿Cómo evitan conflictos (cupos, reservas solapadas, dobles inscripciones)?
--------------------------------------------------------------------------------
RESPUESTA:
1) Unique compuesto en BD/ORM (alumnoId+tallerId).
2) Validación de negocio en services: ConflictException / BadRequestException
   (ej. ya hay sesión abierta hoy; ya inscrito en la salida).
3) Reservas: validarReserva cruza franjas activas y solapes horarios
   (query builder sobre hora_inicio/hora_fin).
4) Salidas: InscripcionSalidaService exige inscripción ACEPTADA al taller
   de esa salida antes de permitir el alta.

Ejemplo de regla (comentario de negocio en inscripción a salidas):
  salida existe + estado visible + alumno ACEPTADO en ese taller + no duplicado.

--------------------------------------------------------------------------------
P8. ¿Cómo validan lo que llega del cliente?
--------------------------------------------------------------------------------
RESPUESTA:
ValidationPipe global en main.ts + DTOs con class-validator:

  app.useGlobalPipes(new ValidationPipe({
    whitelist: true,            // quita campos extra
    forbidNonWhitelisted: true, // error 400 si mandan basura
    transform: true,            // "1" → 1
  }));

Ejemplo LoginDto:
  @IsString() @IsNotEmpty() usuario: string;
  @IsString() @IsNotEmpty() password: string;

CreateReservaDto exige espacio, fecha ISO, tallerId (@IsInt + @Type Number).

Esto separa "forma de los datos" (DTO) de "reglas de negocio" (Service).

--------------------------------------------------------------------------------
P9. ¿Cómo manejan múltiples roles (admin, directiva, profesor, alumno, apoderado)?
--------------------------------------------------------------------------------
RESPUESTA:
Un solo endpoint de login unificado. El JWT distingue:
  role (super_admin / admin / usuario…)
  tipo (admin / directiva / profesor / alumno / apoderado)

Caso especial apoderado: no tiene tabla propia; se autentica con
apoderadoRut / passwords en la fila del Alumno; JWT.sub = alumnoId (hijo).
Portal apoderado llama GET /apoderado/resumen con JwtAuthGuard + assertApoderado.

Frontend: authGuard + métodos can* en AuthRoleService ocultan menús.
Backend: validaciones puntuales por tallerId del profesor, etc.

--------------------------------------------------------------------------------
P10. ¿Notificaciones en tiempo real? ¿Por qué SSE y no WebSockets?
--------------------------------------------------------------------------------
RESPUESTA:
NotificacionService.crear* persiste en tabla notificaciones y emite SSE
(NotificacionStreamService). El frontend usa EventSource; si falla,
poll cada 30s (NotificacionPollService).

SSE es unidireccional servidor→cliente (ideal para "campanita").
WebSockets serían bidireccionales (chat/colaboración); aquí no hacen falta.
Además hay canal email paralelo (MailService / Nodemailer).

--------------------------------------------------------------------------------
P11. ¿El backend sirve solo API o también el frontend?
--------------------------------------------------------------------------------
RESPUESTA:
En desarrollo: Angular :4200 + Nest :3000 (CORS enableCors()).
En despliegue: main.ts puede servir el build de Angular como estáticos
y un fallback SPA a index.html, pero EXCLUYE prefijos API
(API_ROUTE_PREFIXES: /auth, /taller, /alumno…).

Así una sola origin/puerto puede hostear UI + API sin romper el router
de Angular ni las rutas REST.

--------------------------------------------------------------------------------
P12. ¿Qué probaría y qué limitaciones admite del proyecto?
--------------------------------------------------------------------------------
RESPUESTA (madurez de tesis):
Pruebas: unitarias de services (validarReserva, estados de taller,
assertApoderado), e2e de login e inscripción, tests de unique/conflict.

Limitaciones honestas:
  - Guard JWT no global en todas las rutas
  - PBKDF2 con pocas iteraciones / password demo 12345
  - CORS abierto (enableCors sin lista blanca estricta)
  - Parte de autorización aún en frontend
  - Seeds/scripts para datos demo

Mejoras futuras:
  RolesGuard + APP_GUARD global, refresh tokens, rate limit login,
  migraciones TypeORM versionadas, más cobertura de tests, argon2.

--------------------------------------------------------------------------------
P13. Muestre dónde está la separación Controller / Service / Entity.
--------------------------------------------------------------------------------
RESPUESTA:
Controller = HTTP (params, body, status)
Service   = reglas de negocio + repositorios TypeORM
Entity    = mapeo a tabla PostgreSQL

Ejemplo mental de reserva:
  ReservaController.create(@Body dto)
    → ReservaService.create → validarReserva → repository.save
    → entidad Reserva (@Entity('reservas'))

El controller no calcula solapes; el service no arma HTML; la entity
no conoce JWT. Eso es cohesión y bajo acoplamiento (pregunta típica).

================================================================================
  CHEAT SHEET — 6 FLUJOS DEL SISTEMA (1 PÁGINA)
  Reservas de Cancha / Talleres extracurriculares
  Patrón siempre igual: Pantalla → ApiService → Controller → Service → PostgreSQL
================================================================================

FÓRMULA UNIVERSAL
-----------------
  Angular (página)  envía HTTP
  Nest Controller  recibe URL / body   (no hace la regla difícil)
  Nest Service     aplica negocio      (cupos, estados, solapes…)
  TypeORM          lee/escribe
  PostgreSQL       guarda

  Frontend:  frontend/src/app/pages/…  +  services/api.service.ts
  Backend:   src/<modulo>/             +  src/entities/


--------------------------------------------------------------------------------
1) LOGIN                          Quién: todos
--------------------------------------------------------------------------------
Pantalla:  login
API:       POST /auth/login   { usuario, password }
Service:   AuthService busca admin/profesor/alumno/apoderado, verifica hash,
           firma JWT { accessToken, user: { id, role, tipo, tallerId } }
Después:   AuthRoleService guarda token; interceptor manda Bearer siempre
Si apoderado → /portal-apoderado | si no → /dashboard


--------------------------------------------------------------------------------
2) TALLER (publicar actividad)    Quién: coordinación
--------------------------------------------------------------------------------
Pantalla:  gestion-actividades
Estados:   BORRADOR → ESPERA_DOCENTE → ESPERA_HORARIO → PUBLICADO → CERRADO
Pasos:     crear → asignar docente → docente acepta → horario → publicar
API clave: POST /taller
           POST /taller/:id/asignar-docente
           PATCH /taller/:id/horario
           PATCH /taller/:id/publicar
Regla:     no se publica sin docente ACEPTADO + horario definido
Catálogo:  solo PUBLICADO (GET /taller/catalogo)


--------------------------------------------------------------------------------
3) INSCRIPCIÓN ALUMNO             Quién: alumno + profesor
--------------------------------------------------------------------------------
Pantallas: inscripcion-talleres  |  gestion-inscripciones
Estados:   PENDIENTE → ACEPTADO | RECHAZADO
Pasos:     1) GET .../validar  (cupo, horario, publicado, período)
           2) POST /inscripcion-taller  → PENDIENTE
           3) PATCH .../responder       → ACEPTADO / RECHAZADO
Cupo:      capacidad − (PENDIENTE + ACEPTADO)
Unique BD: un alumno una sola fila por taller
Sin ACEPTADO → no entra a asistencia


--------------------------------------------------------------------------------
4) ASISTENCIA (pasar lista)       Quién: profesor
--------------------------------------------------------------------------------
Pantalla:  control-asistencia
Pasos:     1) POST /asistencia/sesion/abrir
              → sesión ABIERTA + 1 registro PRESENTE por alumno ACEPTADO
           2) PATCH .../registros  (marcar AUSENTE) + listaGuardada
           3) PATCH .../cerrar
              → CERRADA + alertas umbral + mail apoderado
Tablas:    sesiones_asistencia  +  registros_asistencia
No hay 2 sesiones ABIERTAS del mismo taller el mismo día


--------------------------------------------------------------------------------
5) RESERVA CANCHA                 Quién: profesor / coordinación
--------------------------------------------------------------------------------
Pantalla:  reservas
Tablas:    franjas_cancha (horarios habilitados) + reservas (ocupación)
Pasos:     1) GET /reserva/disponibilidad  → slots disponible/ocupada
           2) POST /reserva  { fecha, horaInicio, horaFin, tallerId, espacio }
Regla:     franja activa + sin SOLAPE de horarios (mismo día/espacio)
Error:     ConflictException “cancha ya ocupada…”


--------------------------------------------------------------------------------
6) PORTAL APODERADO               Quién: apoderado
--------------------------------------------------------------------------------
Pantalla:  portal-apoderado
Login:     tipo=apoderado ; JWT.sub = id del HIJO (no hay tabla apoderado)
API:       GET /apoderado/resumen   (JwtAuthGuard en toda la clase)
Service:   assertApoderado + talleres ACEPTADOS + asistencia de sesiones CERRADAS
Extra:     proponer inscripción / actividad libre → revisa la directiva
Casi no crea datos nuevos: LEE lo que talleres/inscripción/asistencia ya guardaron

  Apoderado      ver hijo/asistencia, proponer
